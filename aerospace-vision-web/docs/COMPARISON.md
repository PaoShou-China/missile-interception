# Experiment Configuration Studio

Status: V4.2, implemented on 2026-11-21. This document defines the comparison
policy, the registry contract, the frozen data contract and the current
validation status.

## 1. What is compared

The studio is **read-only**. It loads already-generated experiment records and
never re-simulates, retunes or rewrites them.

Current workspace audit:

| Artifact | State | Usable as |
| --- | --- | --- |
| `missile_intercept/output/telemetry.csv` | one 6-DoF shot, 67 276 rows, workspace snapshot | **Run A** (validated payload) |
| `output/batch/batch_results.csv` | 2-row verification remnant | not a campaign |
| `output/validation/validation_results.csv` | envelope sweep, different protocol | not a paired Run B |
| legacy HTML/MD reports | different versions and statistical units | provenance only |

**No independent Run B exists.** The default B selection is therefore the
explicitly labelled synthetic demo, which is excluded from performance claims.
When a user selects any combination without a record, the panel shows
`No Available Experiment` and the Compare action is disabled. Results are never
fabricated.

### Registry-driven dropdowns

`public/data/experiments/registry.json` is the single source of truth for the
four dropdown columns:

| Column | Current entries | Source |
| --- | --- | --- |
| Guidance method | 4 laws: Bezier+ZEM/APN, PIP+ZEM/APN, Bezier+PN, PIP+PN | `missile_intercept/guidance/*.py` |
| Attitude control | 3 profiles: predictive + n_z, uncompensated, no n_z | `missile_intercept/control/autopilot.py`; `config.py` switches |
| Vehicle profile | `lifting-body-2000` (v4) | `missile_intercept/config.py` |
| Scenario | `coastal-intercept` (real), `coastal-intercept-demo` (synthetic) | scenario payload |

The guidance laws are the two implemented midcourse laws (Bezier, PIP) crossed
with the two implemented terminal laws (ZEM/APN, pure PN). The three attitude
controllers are the baseline three-loop and the two documented comparator
switches (`AP_PREDICT_ENABLE=0`, `AP_NZ_LOOP=0`). Every option is backed by a
real deterministic run generated by `missile_intercept/main.py` from the same
launch/target datums, time base and sensor seeds; each payload passed the
adapter integrity checks. The UI is registry-driven: adding an option or record
to the JSON makes it selectable without code changes. Combinations absent from
`experiments` resolve to `null` via `findExperiment()` and are reported, never
approximated.

The matrix intentionally does **not** claim a full factorial campaign. Guidance
laws are compared at the baseline controller, and controllers are compared at
the baseline guidance law. Any other combination (for example PIP + the
uncompensated controller) has no record and shows `No Available Experiment`.

Vehicle profiles are read-only: length, diameter, masses, fin semi-span, version
and source are displayed from the archive. Only visual parameters (model scale,
camera preset, playback rate) are adjustable and they never touch the physical
model or the experiment record.

## 2. Comparison levels

| Level | Rule | Performance claim |
| --- | --- | --- |
| A · Strictly matched | same scenario id, datums, Earth model, start time, units; only method differs | allowed if both validated |
| B · Partially matched | no blocking difference, but recorded differences exist (e.g. commit) | allowed only within the matched scope |
| C · Not directly comparable | scenario/config/datum/time differences, missing validation, or synthetic data | forbidden |

The matcher (`src/compare/validation.ts`) reports every difference with field,
A value, B value and severity. Level C comparisons remain browsable but the UI
states that no algorithm superiority conclusion is produced.

## 3. Data contract

`schemas/comparison-manifest.schema.json` freezes:

- `ComparisonManifest`: protocol, runs, alignment mode, matching status, links.
- `AlgorithmRun`: ids, algorithm/version, commit, scenario, configuration hash,
  seed, trajectory file, data hash, time range, frame, units, validation,
  availability, synthetic flag, notes.
- `ComparisonMetric`: definition, source, aggregation, A/B values, eligibility.
- `ComparisonState`: run ids, comparison time, sync mode, camera, visual mode.

`public/data/compare/comparison.json` is generated from the current payload by
`tools/compare/build_comparison.py`; it records Run A and a pending Run B.

## 4. Time model

Three clocks are kept distinct:

1. **Simulation time** — each run's own recorded time.
2. **Comparison time** — the shared clock used by both views.
3. **Presentation time** — not used here; the explorer owns its own film clock.

Default mode is absolute simulation time. The comparison interval is the
intersection of both runs, so no run is extrapolated; a run outside its range is
hidden and labelled `ENDED`, never frozen as if still running.

`Event-Aligned` is optional. It offsets B so a matching event label coincides
with A and displays a warning that absolute times are not equal. Independent
playback lets each run hold its own time; point-wise difference curves are then
disabled.

## 5. Unified comparison page

There is one page and two 3D layouts; the old four-way mode switcher was removed
to keep the studio simple.

- **Side-by-side**: two canvases, identical camera rule, shared time.
- **Overlay**: both full trajectories in one ECEF frame; fixed colours
  (A `#2f7fd0`, B `#37b9d8`).

Cameras: global, flight, attitude (body axes), control surfaces. Both panes use
Run A's pose as the reference so projection and framing are identical. Sun,
Moon, day/night and atmosphere follow the shared astronomical model.

The lower half of the page contains:

1. **Science charts** — altitude, speed, load and dynamic pressure for A/B.
   Δ(t) charts appear only when the comparison is eligible (matching
   definitions/units and non-synthetic data).
2. **Result summary** — metric, unit, A value, B value, difference and source;
   differences are shown as `N/A` whenever eligibility fails.
3. **Conditions** — guidance/control/vehicle/scenario ids, configuration hash,
   source commit and validation status, plus every matcher issue.

## 6. Swapping and saving

- **Swap A / B** exchanges the selections and loaded runs without reloading.
- **Save selection reference** writes a JSON reference
  (`registry_id`, `generated_from`, timestamp, A/B selection and experiment id)
  to `localStorage` and the clipboard. It is a reference only — no data is
  re-generated.

## 7. Known gaps / NOT RUN

- No paired multi-run campaign is present, so distribution, confidence
  intervals and paired-difference statistics are **NOT RUN**.
- The matrix is not full-factorial: only guidance-at-baseline-controller and
  controller-at-baseline-guidance records exist. Other cross-combinations are
  reported as unavailable.
- The baseline payload was re-simulated from the current working tree so every
  compared run shares one code state; the earlier archived telemetry remains at
  `data/missile-intercept/scenario.json` for the explorer and is not silently
  mixed into a comparison.
- Payload-integrity checks PASS for every run, but an independent scientific
  validation campaign is **NOT RUN**; the UI reports this status per run.
- The synthetic demo exercises UI/difference maths only; it is not a scientific
  result and is not included in any aggregate.
- Comparison rendering is verified in Chromium and WebKit; a long-duration
  dual-canvas soak is **NOT RUN**.
- Legacy hit rates and single-shot miss distances use different statistical
  units and are never presented as an algorithm comparison.
