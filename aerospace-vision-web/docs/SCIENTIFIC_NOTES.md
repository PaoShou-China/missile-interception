# Scientific notes and data audit

## 1. Source

`missile_intercept/output/telemetry.csv` — 67,164 rows × 132 columns, written by
`TelemetryLogger.save_csv` in the source repository. Column meanings are
declared in `missile_intercept/config.py` (`TELEMETRY_COLUMNS`) and the packed
state layout in `missile_intercept/state_schema.py`. The adapter refuses to run
if any required column is missing.

## 2. Converted quantities

All conversions are performed once, in `tools/data-adapter/build_scenario.py`,
and asserted before the payload is written.

### Positions

The source stores both ECI (`m_r*`) and ECEF (`m_ecef_*`). ECEF is used
directly in the renderer. The adapter independently confirms the relation

```
r_ecef(t) = Rz(−ω t) · r_eci(t),   ω = 7.2921150e-5 rad/s,
```

with ECI == ECEF at t = 0. At t = 0 the two agree exactly; at mid-flight the
independently rotated ECI position reproduces the stored ECEF position to
< 1 × 10⁻³ m (numerically, < 1 × 10⁻⁶ m/s in velocity).

### Velocities

```
v_ecef = Rz(−ω t) · (v_eci − ω × r_eci)
```

verified at t ≈ 335.8 s with a 6.8 × 10⁻⁷ m/s residual (CSV print precision).

### Attitudes

`q_w..q_z` are scalar-first, `BODY → ECI`. The renderer needs `BODY → ECEF`:

```
q_ecef_body = q_Rz(−ω t) ⊗ q_eci_body
```

All quaternions are normalised after conversion and sign-aligned to `w ≥ 0` for
a continuous stream. Unit-norm deviation before normalisation is ≤ 8.2 × 10⁻⁷,
consistent with six-decimal CSV output.

### Geodetic

Latitude/longitude/altitude come from the source. The adapter verifies that a
WGS84 LLH→ECEF reconstruction matches the telemetry ECEF position to 7.3 cm
maximum. Browser-side validation repeats this check at the 1 m level.

## 3. Speed semantics (audit finding)

The source column `m_speed` is **inertial** speed, `|v_ECI|`. At t = 0 it reads
356.78 m/s while the vehicle is at rest relative to the Earth (ECEF velocity
= 0); the value equals the Earth-rotation transport speed ω·r. The existing
static report plotted this column under the label “speed”.

This platform defines:

- **Speed** = `|v_ECEF|`, the Earth-relative speed — physically the right
  quantity for ground track, dynamic pressure and Mach comparisons.
- **Mach** = air-relative speed / local sound speed. The adapter verifies
  `airspeed = |v_ECEF|` exactly and that Mach differs from
  `airspeed / sound_speed` by at most 0.05 (wind correction). The difference is
  documented rather than “fixed”.
- The manifest records the source semantics in the `speed-semantics` and
  `speed-and-mach-semantics` checks so the distinction is auditable.

## 4. Time and interpolation

Sampling is non-uniform by design: 1,500 uniform points plus protected indices
at phase transitions, seeker lock, handover, apogee, maximum dynamic pressure,
closest approach, and the final row. Protected indices ensure events that fall
between uniform samples are preserved exactly.

- Position uses cubic Hermite with the telemetry velocity as the node tangent,
  so every stored sample is reproduced exactly and the tangent is physical.
- Attitude uses shortest-arc SLERP; endpoints are exact and the result is
  renormalised.
- Scalars (Mach, q, load, mass) are linear; phase/flags use nearest-neighbour.
- Interpolation never crosses a segment boundary, so event discontinuities are
  not smoothed into false motion.
- Sampling outside [t₀, tₙ] clamps instead of extrapolating.

The TS test suite compares the interpolated path’s implied speed with the
telemetry speed at 0.02 s intervals over the whole flight; the worst relative
deviation is under 3%.

## 5. Derived quantities (explicitly labelled)

- **Target attitude**: the source telemetry has target position/velocity but no
  target attitude. The adapter derives a `BODY → ECEF` quaternion whose +X axis
  follows the ECEF velocity, with a stable up-reference. This affects only the
  target’s visual orientation, never its position.
- **NED roll/pitch/yaw** in the HUD: computed from the stored BODY→ECEF
  quaternion and the local WGS84 NED basis, decomposed as ZYX. Unit-tested
  against an independently constructed DCM.
- **Sun direction**: V4 replaces the fixed direction with a computed sun/moon
  position (`src/scientific/astronomy.ts`) derived from the declared demo UTC
  plus elapsed simulation time. It drives lighting and the terminator only; it
  is not used in the trajectory solution.

## 7. V4 additions

### 7.1 Actuator channels

The payload now carries the recorded `fin_up/down/left/right` (rad) and body
rates `p/q/r` (rad/s). The adapter asserts that both channel groups are present
and non-zero; the unit test does the same on the shipped JSON. The fin meshes
rotate from these recorded values. Fin geometry is schematic (not CAD), which
is disclosed in `RESULT_PROVENANCE.md`.

### 7.2 Experiment manifest and reproducibility

`experiment` records `kind=simulation`, the solver description, sampling step,
campaign dispersion settings, and a `reproducibility` verdict. The adapter sets
`unreproducible-current-artifacts` when the batch artifact holds fewer than 50
cases, which is the case after the 2-row verification overwrite.

### 7.3 Astronomy accuracy and limits

Solar position uses NOAA low-precision coordinates; lunar position uses a
truncated Meeus-style series. Unit tests check unit length, equinox declination
(< 1°), solstice declination (22.5°–24.5°), day/night at the launch site, and
drift over the mission. Accuracy is suitable for lighting, not navigation.

### 7.4 Legacy audit outcome

The old overview is internally inconsistent (86 % and 79 % in one section) and
its 100-case campaign cannot be rebuilt from current artifacts. `DATA_AUDIT.md`
records both values with file/line references; neither is presented as a
verified hit rate.

### 7.5 Cinematic time is not simulation time

The 180 s film maps linearly onto the mission for presentation. Every displayed
observable still comes from the single simulation clock; the film clock never
feeds the data pipeline.
